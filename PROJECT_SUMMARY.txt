1. EXECUTIVE SUMMARY & CORE PURPOSE
================================================================================

Serving Large Language Models (LLMs) in production introduces major engineering
challenges:
  * High round-trip latency (often 500ms to 3000ms+ per inference call).
  * High operational compute and cloud API token costs.
  * Strict rate-limiting constraints on external LLM inference providers.
  * Redundant generation when different users ask identical or semantically
    equivalent questions (e.g., "What is the capital of France?" vs.
    "Which city is France's capital?").

This project solves these challenges by implementing an enterprise-grade,
low-latency Two-Tier LLM Caching and Inference Engine paired with an interactive
real-time web dashboard, evaluation suite, and benchmarking tools.

KEY HIGHLIGHTS:
  * Tier 1 (Exact Match Cache): Instant O(1) hash map lookup for identical
    prompts, yielding sub-millisecond latency (0.0 ms model execution time).
  * Tier 2 (Semantic Embedding Cache): Dense vector similarity matching using
    a local sentence embedding model (all-MiniLM-L6-v2, 384 dimensions). It
    intercepts paraphrased queries that meet or exceed a configurable cosine
    similarity threshold (e.g., 0.90).
  * Upstream LLM Fallback: When both cache tiers miss, queries are asynchronously
    dispatched to Groq Cloud's ultra-fast LLM API (defaulting to
    'qwen/qwen3.8-27b'). The newly generated output and its normalized embedding
    are immediately indexed into the cache.
  * Real-Time Observability: Full structured telemetry logging to JSONL format
    capturing queue wait time, model execution time, total latency, token usage,
    cache hit/miss status, similarity scores, and matched prompt keys.
  * Full-Featured Web UI: A single-page application (index.html) featuring a
    live interactive playground, cache inspector, live vector similarity viewer,
    telemetry charts, and request drill-down modals.

3. EVOLUTIONARY DEVELOPMENT PHASES (PHASES 1 TO 4)
================================================================================

The project reflects an evolutionary engineering progression, starting from a
naive synchronous server and culminating in a production-ready cached system:

--------------------------------------------------------------------------------
PHASE 1: Stage A - Baseline Synchronous Inference Server
--------------------------------------------------------------------------------
Directory: Phase 1/
Files:
  * server_stage_a.py (FastAPI server, port 8000)
  * test_stage_a.py (Automated smoke test)

Core Mechanics:
  * Loads Hugging Face 'gpt2' locally onto CPU.
  * Every incoming HTTP request directly calls `model.generate()` synchronously
    inside the route handler on the main event loop thread.
  * Demonstrates the primary bottleneck: concurrency blocking. Multiple clients
    experience serialization delays and head-of-line blocking.

--------------------------------------------------------------------------------
PHASE 2: Stage B - Asynchronous Request Queue & Background Worker
--------------------------------------------------------------------------------
Directory: Phase 2/
Files:
  * server_stage_b.py (FastAPI server with background worker)
  * test_stage_b.py (Concurrency tests)

Core Mechanics:
  * Decouples HTTP request ingestion from heavy PyTorch execution.
  * Uses `asyncio.Queue` to buffer incoming requests (`RequestItem`).
  * Dedicated background worker task continuously pops requests and offloads
    model execution to a thread pool via `loop.run_in_executor()`.
  * Introduces futures (`asyncio.Future`) to resolve responses back to the
    awaiting HTTP endpoint without blocking the server loop.

--------------------------------------------------------------------------------
PHASE 3: Stage C - Dynamic Batching with Window Timeout
--------------------------------------------------------------------------------
Directory: Phase 3/
Files:
  * server_stage_c.py (Batched inference server)
  * test_stage_c.py (Batch throughput test)

Core Mechanics:
  * Accumulates multiple requests from the queue into batches up to
    `MAX_BATCH_SIZE = 4` or until a deadline `BATCH_TIMEOUT = 0.2` seconds expires.
  * Implements left-padding (`tokenizer.padding_side = "left"`) with attention
    masks required for causal language models generating text simultaneously.
  * Demonstrates higher overall token throughput (Tokens Per Second) under
    heavy concurrent load.

--------------------------------------------------------------------------------
PHASE 4: Stage D - In-Memory Exact-Match Caching
--------------------------------------------------------------------------------
Directory: Phase 4/
Files:
  * server_stage_d.py (Batched server with exact caching)
  * test_stage_d.py (Cache hit & eviction verification)

Core Mechanics:
  * Introduces an in-memory dictionary cache mapping `(normalized_prompt, max_tokens)`
    to pre-generated text completions.
  * Exact cache hits bypass the request queue and PyTorch inference entirely,
    returning results instantaneously with 0 ms queue and compute time.
  * Highlights the limitation of exact matching: slight variations in wording,
    punctuation, or phrasing result in unnecessary cache misses.

4. ROOT PRODUCTION SYSTEM DEEP DIVE (STAGE E)
================================================================================

The root system represents the complete, integrated production application:
  * File: server.py
  * Default Port: 8004
  * Model Backend: Groq Cloud API ('qwen/qwen3.8-27b')
  * Local Semantic Engine: 'sentence-transformers/all-MiniLM-L6-v2'

--------------------------------------------------------------------------------
4.1. TIER 1: EXACT MATCH CACHE ENGINE
--------------------------------------------------------------------------------
The exact-match tier executes with O(1) time complexity. It utilizes a
3-stage cascade lookup strategy to maximize hits while preserving token fidelity:

1. Strict Match:
   Direct key lookup on `(cleaned_prompt, max_new_tokens)`.
2. Clean Prompt Match across Token Budgets:
   Matches identical prompt strings even if `max_new_tokens` varies (prioritizing
   the entry closest to the requested token length, then by most recent). This
   ensures pre-warmed FAQ items hit immediately.
3. Normalized Prompt Match:
   Normalizes whitespace and converts text to lowercase. This catches case
   variations and trailing spaces without invoking vector embeddings.

TTL Expiration:
  * Entries older than `cache_ttl` (default 3600s / 1 hour) are evicted lazily
    during lookup and inspection cycles.

--------------------------------------------------------------------------------
4.2. TIER 2: DENSE SEMANTIC VECTOR EMBEDDING CACHE ENGINE
--------------------------------------------------------------------------------
When Tier 1 misses, Tier 2 evaluates semantic intent:

1. Local Vector Representation:
   Uses Hugging Face `transformers` running `sentence-transformers/all-MiniLM-L6-v2`.
   The model computes contextual token embeddings locally on CPU in eval mode.
2. Attention-Masked Mean Pooling:
   Calculates the mean of all token vectors weighted by attention masks:
     mean_pooled = sum(token_embeddings * attention_mask) / clamp(sum(mask))
3. L2 Normalization:
   Normalizes the 384-dimensional vector onto the unit hypersphere:
     embedding = torch.nn.functional.normalize(mean_pooled, p=2, dim=1)
4. Cosine Similarity via Dot Product:
   Because vectors are L2-normalized, cosine similarity equals the dot product:
     similarity = torch.dot(query_vector, cached_vector)
5. Threshold Evaluation:
   The candidate with the highest similarity score is evaluated against
   `similarity_threshold` (default 0.90, adjustable from 0.50 to 1.00). If the
   score meets or exceeds the threshold, the cached completion is returned.
6. Golden FAQ Seeding:
   Includes 8 built-in authoritative reference Q&As covering physics, chemistry,
   computing, biology, geography, and Python programming. Can be pre-warmed via
   `/api/seed_defaults` or custom datasets via `/api/seed_cache`.

--------------------------------------------------------------------------------
4.3. UPSTREAM FALLBACK: GROQ CLOUD LLM INFERENCE ENGINE
--------------------------------------------------------------------------------
When both Tier 1 and Tier 2 miss:
  * The server makes an asynchronous HTTP POST request using `httpx.AsyncClient`
    to `https://api.groq.com/openai/v1/chat/completions`.
  * Authenticates via `GROQ_API_KEY` from `.env`.
  * Generates high-speed completions using Groq's LPU architecture (typically
    under 250-600ms).
  * Automatically stores the new output, prompt token counts, completion token
    counts, and computed prompt embedding into the `TwoTierCache`.

--------------------------------------------------------------------------------
4.4. TELEMETRY LOGGING & OBSERVABILITY PIPELINE
--------------------------------------------------------------------------------
Every processed request appends an immutable JSON record to
`telemetry_metrics.jsonl`. Logged fields include:
  * `request_id`: Unique identifier (e.g., "req-a1b2c3d4").
  * `timestamp`: Human-readable local date-time string.
  * `prompt`: Full prompt text submitted by client.
  * `generated_text`: Complete generated text.
  * `prompt_char_len`: String character length.
  * `queue_time_ms`: Queue wait time (ms).
  * `processing_time_ms`: Model execution duration (0.0 ms for cache hits).
  * `total_latency_ms`: Total roundtrip time from server arrival to response.
  * `cache_hit`: Boolean flag indicating if cache satisfied request.
  * `match_type`: Match classification: "exact", "semantic", or "none".
  * `similarity_score`: Float similarity score (for semantic matches).
  * `matched_prompt`: The cached key prompt that triggered the hit.
  * `prompt_tokens`, `generated_tokens`, `total_model_tokens`: Token metrics.
  * `cache_enabled`, `semantic_cache_enabled`, `similarity_threshold`: Config flags.

6. HTTP API ENDPOINTS & REQUEST/RESPONSE CONTRACTS
================================================================================

Core Service Endpoints:
-----------------------
* GET / or GET /playground
  Serves index.html single-page application.

* POST /generate
  Query Parameters:
    - enable_cache (bool, default true): Toggle Tier 1 cache.
    - enable_semantic_cache (bool, default true): Toggle Tier 2 cache.
    - similarity_threshold (float, default 0.90): Minimum cosine score for hit.
    - cache_ttl (float, default 3600.0): Cache Time-To-Live in seconds.
  Request Body:
    { "prompt": "What is water made of?", "max_new_tokens": 30 }
  Response:
    {
      "request_id": "req-9c4b12df",
      "prompt": "What is water made of?",
      "generated_text": "Water is composed of two hydrogen atoms...",
      "queue_wait_time_ms": 0.0,
      "processing_time_ms": 0.0,
      "total_latency_ms": 3.45,
      "batch_size": 0,
      "cache_hit": true,
      "match_type": "semantic",
      "similarity_score": 0.9234,
      "matched_prompt": "What is the chemical composition of water?",
      "prompt_tokens": 6,
      "generated_tokens": 28,
      "total_model_tokens": 0
    }

* GET /api/status
  Returns server health, stage descriptor, active LLM model, cache count, and TTL.

* GET /api/cache_entries
  Returns list of all active cache entries with prompts, max token budgets,
  response previews, timestamps, and age in seconds.

* POST /clear_cache
  Query Parameter:
    - prompt (optional string): If provided, evicts only that specific prompt.
      If omitted, purges the entire cache.

* POST /api/seed_defaults
  Pre-warms the cache with 8 golden FAQ question-answer pairs.

* POST /api/seed_cache
  Accepts a custom list of `{ "prompt": "...", "response_text": "...", "max_new_tokens": 40 }`
  objects to seed domain knowledge into the cache.

* POST /api/vector_inspect
  Calculates the query prompt embedding and performs k-Nearest-Neighbor (k-NN)
  similarity search across all cached entries.
  Request:
    { "prompt": "water boiling temp", "top_k": 5, "similarity_threshold": 0.90 }
  Returns neighbors ranked by similarity score with threshold pass/fail flags.

* GET /api/logs
  Query Parameter: `limit` (default 50). Returns recent telemetry log entries
  in reverse chronological order.

* GET /api/request/{request_id}
  Retrieves the full telemetry record for a specific request ID.

* GET /api/benchmark_results, GET /api/evaluation_results, GET /api/prompt_results
  Returns saved JSON outputs from the benchmarking and evaluation scripts.

8. EVALUATION, BENCHMARKING & SEMANTIC POOLING ANALYSIS
================================================================================

A key engineering contribution of this project is the empirical evaluation of
semantic caching accuracy using sentence embeddings:

--------------------------------------------------------------------------------
Semantic Pooling Accuracy & False-Positive Traps
--------------------------------------------------------------------------------
Evaluation script: evaluate_semantic_pooling.py
Evaluated against 22 curated test pairs:
  * 11 True Paraphrases (e.g., "What is the capital of France?" vs.
    "Which city is France's capital?") -> Ground Truth: POOL
  * 11 Negative Distractors & Traps -> Ground Truth: REJECT:
    - Entity Swaps ("capital of France" vs. "capital of Spain")
    - Negation Traps ("Why is Python fast..." vs. "Why is Python NOT fast...")
    - Directional Flips ("USD to EUR" vs. "EUR to USD")
    - Action Verb Swaps ("train a model" vs. "save a model")
    - Temporal Shifts ("World Cup in 2018" vs. "World Cup in 2022")
    - Antonym Swaps ("ascending order" vs. "descending order")
    - Domain Shifts ("Python programming" vs. "Python snake diet")
    - Scale Shifts ("Generate 5 random..." vs. "Generate 500 random...")
    - Role Reversals ("dog bites human" vs. "human bites dog")

Threshold Sweep Results:
  +-----------+----+----+----+----+-----------+--------+----------+-----------------------+
  | Threshold | TP | FP | FN | TN | Precision | Recall | Accuracy | Risk Level            |
  +-----------+----+----+----+----+-----------+--------+----------+-----------------------+
  | 0.80      | 11 |  5 |  0 |  6 |    68.8%  | 100.0% |   77.3%  | CRITICAL (High FPs)   |
  | 0.85      | 11 |  2 |  0 |  9 |    84.6%  | 100.0% |   90.9%  | HIGH (2 FPs)          |
  | 0.90      | 10 |  0 |  1 | 11 |   100.0%  |  90.9% |   95.5%  | SAFE (Zero FPs)       |
  | 0.92      |  8 |  0 |  3 | 11 |   100.0%  |  72.7% |   86.4%  | SAFE (Zero FPs)       |
  | 0.95      |  3 |  0 |  8 | 11 |   100.0%  |  27.3% |   63.6%  | SAFE (Ultra-Strict)   |
  +-----------+----+----+----+----+-----------+--------+----------+-----------------------+

Key Engineering Finding:
  * At threshold 0.80, the system exhibits severe false-positive errors (68.8%
    precision), answering questions about Spain with answers about France.
  * At threshold 0.90 to 0.92, the system achieves 100% Precision with ZERO
    false positives while retaining 73-91% recall on true paraphrases.
  * Therefore, 0.90 is selected as the default production threshold.

--------------------------------------------------------------------------------
Performance & Latency Acceleration
--------------------------------------------------------------------------------
Benchmarking script: benchmark.py
Comparing cold LLM execution vs. cached execution:
  * Full Cache Miss (Groq LLM): ~350ms - 1200ms total latency.
  * Tier 2 Semantic Hit: ~3ms - 8ms total latency (98%+ latency reduction).
  * Tier 1 Exact Hit: ~0.5ms - 2ms total latency (99.8%+ latency reduction).
  * System throughput (RPS) scales exponentially when recurring or paraphrased
    queries are intercepted by the in-memory cache.
